# Railway deployment

Dragons Market uses one pnpm workspace, one Railway project and separately deployed services. This follows the live Agent API and TLA layout inspected on 6 November 2026: root build/start commands, builds from the repository root, service-specific watch paths, private PostgreSQL references, and a deployment gate for database changes. Existing `backend/`, `web/` and `mcp/` paths remain intact; the Rust contracts are deployed to NEAR separately.

Project: [dragons-market](https://railway.com/project/489b02ad-fd74-4413-ab91-835da8b86542), the team's Railway workspace, `production` environment. A Railway environment named production does not select a NEAR network.

The agent worker owns partner credentials and sealed grants. The server cannot read those grants or write agent operations. MCP calls the server over Railway's private network. No Redis service is needed by the current implementation.

The agent worker now uses `/health/ready` and `check-agent-worker.js` before deployment. These verify its configured manifest, schema and restricted login, not the validity of an unavailable external API key. Defuse portal credentials are still pending. [KEEPER.md](KEEPER.md) documents preparation, guarded signing, the dedicated role, volume initialization and journal recovery. Signing remains disabled on Railway. The service settings include this additional job; `configure.mjs` therefore requires creating it before applying the full inventory. Do not apply the new inventory or deploy activation workers as part of a foundation release.

Before releasing this revision's foundation, update the `server` and `database-release` watch patterns to include `contracts/keeper/**`, matching `services.json`; the release verifier checks those settings too. This can be done for those two existing services without creating or deploying the keeper. Apply agent-worker and keeper settings separately when their activation dependencies are ready.

`indexer` copies finalized contract events into Postgres so the API can answer quickly. `reconcile` compares indexed liabilities with on-chain collateral and records discrepancies; it does not silently credit unexplained funds. `verify-chain` checks the database's stored block links, event counts and checkpoint consistency. `prices` collects external price evidence for settlement. Separate processes give each job its own failure lifecycle and database privileges. Only the indexer owns ingestion writes; price and reconciliation jobs cannot alter wallet sessions or agent grants.

`database-release` is a one-time maintenance job for each release, not a permanently running server. `verify-chain` uses `0 */6 * * *` and exits after each check rather than retaining an idle Node process. The other workers run loops because their work needs continuous ingestion or more precise timing than Railway cron provides. An undeployed worker consumes no runtime compute.

`prices` collects evidence; it does not publish signed prices or run the contract keeper. Round prices are signed by the separate `publishers` service with the publisher database role, configured through the [activation workflow](ACTIVATED-RELEASE.md#price-publishers).

## Toolchain and service settings

Use Node **24.22.2** and pnpm **10.33.0**. Install from the repository root with `pnpm install --frozen-lockfile`. The three application packages share `pnpm-lock.yaml`.

[deploy/railway/services.json](../deploy/railway/services.json) records build, start, healthcheck, watch and restart settings. After creating the named services and linking the CLI to the intended environment, apply them from a terminal:

```sh
railway link --project 489b02ad-fd74-4413-ab91-835da8b86542 --environment production
node deploy/railway/configure.mjs 489b02ad-fd74-4413-ab91-835da8b86542 dfda2a3a-a864-4e86-ab25-2299069f7729
```

The script verifies both the project and environment before applying settings, then reads the result back. It does not create services, install secrets, modify PostgreSQL, connect GitHub or change domains. These settings use Railway's service configuration mechanism. An empty build command clears the old Railpack command; CLI JSON null did not clear it during the November deployment.

All application services use multi-stage Docker builds from the repository root. Dependency manifests are copied before source so ordinary edits can reuse the dependency layer. Backend and MCP use a digest-pinned Google Distroless Node 24 runtime (24.22.2, UID 65532) containing production package dependencies, without a shell, npm, pnpm or Yarn. Application files are root-owned and readable by the runtime user. Web exports Next at build time and runs digest-pinned Caddy 2.11.9 as UID 1000; Node and frontend build dependencies are absent from its runtime image. Conditional local publisher/feed mounts must grant UID 65532 the intended access. Shell-based debugging is unavailable in the Distroless images; use startup logs, health/operator routes and a separately controlled debug environment.

Website fonts are bundled under `web/app/fonts` with their upstream source and licenses. `next/font/local` serves them as hashed static assets. Font selection no longer calls Google during builds; the production build was verified without outbound networking. This fixes the external font-response parser failure observed in the first public deployment attempt.

The web build prepares `web/out-caddy` from the untouched static export. Caddy templates only these build-owned HTML files, generating a cryptographically random nonce per response for Next scripts, script preloads and the wallet connector's sandboxed frames. HTML is `no-store`; hashed bundles retain immutable caching. No Node server or additional Railway service is introduced. Never template API responses, uploads or user content. The build rejects the reserved template delimiters; request values are not interpolated. The CSP blocks unapproved inline scripts, script event handlers, eval, objects, framing and native form submission. Inline styles and HTTPS/WSS wallet connections remain allowed for compatibility with wallet executors and their RPC/relay endpoints; this is not an outbound-domain allowlist. CI runs `pnpm --filter web test:csp` against pinned Caddy and Chromium, including a fixture wallet connection, client navigation and blocked injection attempts. This does not certify every external wallet or perform a real signature.

Backend and MCP Dockerfiles declare no build arguments for credentials. The web Dockerfile declares only public `NEXT_PUBLIC_*` configuration. Each build asserts that database, partner, grant and operator credentials are absent from its build environment. `.dockerignore` excludes local environment files, keys and runtime state. Do not add secret `ARG` or `ENV` declarations to these build stages. Railway's [Docker documentation](https://docs.railway.com/builds/dockerfiles) describes this argument boundary.

All services use one replica in US West. Runtime ceilings configured in Railway are 0.5 GB RAM and 0.5 vCPU for web/MCP; 0.5 GB and 1 vCPU for server, release, agent worker, reconcile, verify-chain and prices; 1 GB and 1 vCPU for Postgres/indexer. These are ceilings, not reserved resource charges. Raise a limit only with workload evidence; inspect memory, CPU, database pool saturation and job lag before increasing replicas. Current per-client limits are process-local, so replica changes need a rate-limit review. Independent backend services can still trigger separate builds; targeted watch paths and Docker layer reuse reduce that work without adding an image-promotion pipeline.

## Database credentials and release order

Postgres uses Railway's official image and a volume at `/var/lib/postgresql/data`. Keep it private. The migration owner URL is referenced only by `database-release` as `${{Postgres.DATABASE_URL}}`.

The release service holds five independent, randomly generated passwords: `API_DB_PASSWORD`, `INDEXER_DB_PASSWORD`, `WORKER_DB_PASSWORD`, `PUBLISHER_DB_PASSWORD`, `AGENT_DB_PASSWORD`. Each is 32 random bytes encoded as 64 lowercase hexadecimal characters. Preserve these values across releases; changing one rotates that login's password.

Runtime services reference their own login. For example, server `DATABASE_URL` is:

```text
postgresql://dm_api_login:${{database-release.API_DB_PASSWORD}}@${{Postgres.PGHOST}}:${{Postgres.PGPORT}}/${{Postgres.PGDATABASE}}
```

Use `dm_indexer_login`, `dm_worker_login` or `dm_agent_login` and the corresponding password reference on other services. Never place the owner URL on a public service.

Release in this order:

1. Run `pnpm typecheck`, `pnpm lint`, `pnpm test`, database integration tests and `pnpm build`. `pnpm test:release` and `pnpm --filter dragons-market-backend test:backup` require a disposable PostgreSQL cluster without existing `dm_*` roles; run them serially. The backup test also needs PostgreSQL 18 clients.
2. Deploy `database-release` from the candidate source. Its logs must report migrations applied and service roles ready. It uses checksum verification, advisory locks and transactional role grants; rerunning the same release applies zero migrations. Restart policy is `NEVER` because successful exit is expected.
3. Deploy `server`. Its pre-deploy command `node dist/src/check-database.js` rejects schema drift and owner/superuser runtime credentials. Railway checks `/health/ready` before routing traffic.
4. Deploy `mcp` and `web`. MCP checks `/health`; web checks `/health/live`.
5. After approving the chain manifest and historical-ingestion plan, deploy the read-only workers. Indexer, reconcile, verify-chain and prices use `node dist/src/check-database.js --require-mainnet-deployment`: current schema, an exactly registered mainnet manifest and a restricted database role are required. Financial activation has a separate strict preflight below.

After deployment, run `node deploy/railway/smoke.mjs <web-origin> <server-origin> <mcp-origin>` to check exported routes, genuine 404s, static asset caching, database readiness and MCP liveness. This does not perform wallet or trading actions.

For a local-source deployment, run `railway up --detach --service <name>` from the repo root. Always specify the service; CLI link state can otherwise target Postgres or another service. The initial deployment uses CLI uploads. Keep Railway's direct GitHub autodeploy connection disabled: the release workflow below owns deployment order and cadence. Build checks must never run migrations against the live database.

## GitHub CI and deliberate releases

Develop and review these changes in private `SHC-Labs/Dragons-Market`. Nameless publishes the selected changes to public `SHC-Labs/DragonsMarket`; releases accept only that public repository's `main`. Both repositories use the same selective PR checks. Private runners consume the organization's Actions allowance/budget; public standard runners do not incur compute charges. Keep production credentials in the public repository's protected environment. A public sync that must omit private contributor identities needs a fresh commit from copied changes; merging or cherry-picking preserves author metadata.

Routine PRs run quick checks for affected components. Superseding updates cancel the old PR run, and merging does not start another identical push workflow. Docs-only changes run the CI policy tests and report the required checks without dependency installation. Web changes run web types, lint and unit tests; backend changes run backend/MCP tests and real PostgreSQL integration/release tests; MCP changes run protocol/types tests. Keeper changes run Node keeper/backend/database checks without compiling Rust. Rust changes run formatting and native contract unit tests in one cached job. Browser security/wallet configuration, backup scripts and shared build/workflow inputs select their corresponding browser or recovery integrations. Unknown source paths conservatively select broad quick checks. Diff detection includes deletions and both sides of renames; inability to read the diff fails the check.

The application job has a 12-minute limit; Rust unit checks have a 20-minute limit; keeper checks have a five-minute limit. These are failure ceilings, not predicted runtime or a monthly spending cap. No ordinary PR starts Clippy's full workspace pass or the eight sandbox shards. Keep the organization's hard spending cap and review actual aggregate runner time; parallel jobs are billed separately. The private `applications` and `contracts` workflows remain disabled following the 9 November budget exhaustion. Re-enable them only after this selective policy reaches private `main` and active development branches; old revisions can still contain expensive triggers. This document does not mean that re-enablement has occurred.

[.github/workflows/agents.yml](../.github/workflows/agents.yml) retains the required `agents` name and is reusable by releases. Manual dispatch defaults to quick checks across all components. Selecting `full` runs all application checks, PostgreSQL 18 integration/release/backup-restore tests, production builds and the Caddy/Chromium wallet/CSP fixture. PostgreSQL starts only when needed, uses disposable test data and binds to localhost. No production secrets or environment enter validation. The restore test verifies full fixture data, schema, sequences and reapplied runtime grants. Manual full validation in the private repository additionally requires `paid_private_checks=true`; it is never inferred from an ordinary PR or push.

The Rust workflow's `contract-checks` gate always reports and requires every selected job to succeed. Manual `full` validation adds all Clippy and sandbox checks, including the compiled-contract agent/keeper/DAO integration on shard zero. Every Cargo integration target is discovered and partitioned across eight jobs, each using two test threads. Full private validation requires the separate paid opt-in and can still consume hundreds of runner minutes; public release validation is the normal full-suite path. A quick green PR is evidence for the selected checks, not full release certification. A failed quick check stays failed: investigate it, then request full validation if useful rather than automatically multiplying runner costs.

[.github/workflows/deploy.yml](../.github/workflows/deploy.yml) has only a manual `workflow_dispatch` trigger. On public `main`, choose **check** to validate credentials, configuration and recent backups without uploading code or repeating the full suite. Choose **deploy** to run both complete validation workflows against the selected immutable commit before the protected production job can start. [Activate Railway](../.github/workflows/activate.yml) uses the same rule. A failed, cancelled or unexpectedly skipped validation blocks deployment. The configuration-only action is not release certification. After validation, an authorized reviewer must review the commit and approve the `production` environment job. The environment allows only `main`, requires a configured reviewer and disallows administrator bypass. Self-review is allowed so the account owner can operate this personal project without another reviewer. HTTP smoke checks follow deployment.

The deploy job checks out the same immutable commit with Git credentials disabled. It installs pinned Railway CLI 4.36.1 before exposing the environment's `RAILWAY_TOKEN` to the release step. Supply a fresh project token scoped to Dragons Market's production environment, not a personal or workspace token. It can deploy services in that environment, so protect it as a production credential. Database passwords, partner keys and grant keys stay in Railway.

### Ingress and monitoring

Railway overwrites `X-Real-IP` on its public HTTP edge. Live probes verified that forged `X-Real-IP` and `X-Forwarded-For` values were replaced. Its socket peer addresses and X-Forwarded-For hop count are not a stable contract. Server uses `TRUSTED_PROXY_HEADER=x-real-ip`, `TRUSTED_PROXY_HOPS=1` and `TRUSTED_PROXY_ADDRESSES=0.0.0.0/0,::/0` for this Railway environment. This deliberately trusts forwarding headers from every peer in the environment for rate-limit identity only; it is not proof of an authenticated edge connection. Other services in the same project/environment can reach this listener directly. Keep every service here trusted, add no public TCP proxy, and isolate any future untrusted workload in a different environment/project. Wallet signatures, sessions, ownership and worker authentication remain mandatory regardless of claimed client IP. See Railway's [published trust-boundary discussion](https://station.railway.com/questions/supported-client-ip-trust-boundary-for-f-0e4c52d9).

For deployments with a stable proxy allowlist, use the actual proxy addresses instead. The default trusts no forwarded headers. `/v1/operator/ingress` returns sanitized peer/client identity details only with the operator bearer token; it exists to detect ingress drift without logging credentials. Never put that token in URLs or browser bundles.

MCP uses the same trusted-environment boundary through `MCP_TRUSTED_PROXY_ADDRESSES`. It accepts only a single valid `X-Real-IP` from an allowlisted socket peer, ignores `X-Forwarded-For`, and rejects missing/malformed identity from a trusted proxy. Other deployments default to the real socket address. IPv4 aliases normalize together and IPv6 addresses share a /64 allowance. Fresh-token checks are limited to 60 per minute per caller, accepted tokens to 60 per minute per token; session checks still verify revocation every time. At most four checks per caller and 32 total may be pending. Caller state is bounded at 10,000 entries without evicting active windows. Rejections return 429 with Retry-After. Clients behind one NAT share an allowance; this is not distributed denial-of-service protection. After deployment, repeat the ingress spoof probe and check that a malformed-token request through the public MCP domain returns 401, not an identity/configuration failure.

Health GET/HEAD requests bypass user request allowances. Readiness coalesces concurrent database checks and caches the outcome for two seconds. MCP's new `/health/ready` checks the API and its database over the private network with a five-second timeout and two-second cache; `/health` remains process liveness. Login challenge allowances apply only to POST requests from the configured Origin. These controls are covered by tests. Railway's deployment health check is not continuous uptime monitoring.

[.github/workflows/monitor.yml](../.github/workflows/monitor.yml) provides a secret-free HTTPS smoke check every 15 minutes after the public sync, first successful deployment and repository variable `PRODUCTION_MONITOR_ENABLED=true`. It performs no build or wallet operation and fails on degraded backend service status. GitHub scheduling is best-effort; pair it with Railway Pro resource alerts and enable failed-workflow notifications for the operator. The schedule is deliberately not active before the new MCP readiness route is deployed. See [OPERATIONS.md](OPERATIONS.md).

The prepared response hardening adds HSTS, anti-framing and MIME protections to API/MCP, disables executable document content on their JSON/text endpoints, and adds HSTS, camera/microphone/location restrictions and base/object/frame CSP directives to the static web server. The web policy is not a complete script allowlist and does not by itself prevent every XSS class. HSTS does not use `includeSubDomains` or preload, so unrelated future subdomains are not forced into this policy.
